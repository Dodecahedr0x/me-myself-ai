# Desktop workspace

**Status** — Implementation contract. Covers [US-01 through US-16](../user-stories.md) at the dashboard boundary. The draft [inbox, focus card and board](inbox-experience.md) will replace the Home and Tasks layout described here. Until it ships, this spec describes the implemented app.

Home summarizes the task queue, pending suggestions, recent activity, projects and style reviews. Tasks needing attention appear first. The status counts open the corresponding filtered queue. Home offers task creation and shows the current agent provider and delivery mode. Its Connections section contains a single **Manage connections** button that opens the Connections page, where the user can choose providers and inspect accounts. Tasks also offers suggestions and the full searchable queue. Activity contains the full timeline.

Use warm white surfaces, graphite text and green actions throughout the workspace. Task status is written out, with an amber margin marker on rows that need a decision. Keep the task title and preview together. In activity logs, align local event times in a column next to the event description and show the date for earlier days. At narrow widths, filters and actions can wrap. Keyboard focus stays visible on rows, links and controls.

Each connected account opens its own chronological activity log. Slack workspaces include their monitored channels and GitHub accounts include their repositories. Each Google address and enabled desktop chat source has an independent log. Use stable source IDs so renaming an account cannot mix its history with another account. Include sync outcomes, observed activity and related task or delivery records. Previously recorded events can be attributed when their stored source is known. Opening a log preserves access to the full timeline via its connection filter. A connection with no recorded activity has a distinct empty state.

Task details show the trigger, available results, completion evidence, linked activity, commitments, and worktree when present. A review presents the full proposed content, sending account, destination, and action version. Approving submits exactly the version on screen. Changing a proposal through feedback requires another review. A question can be answered locally. Failures expose recovery options consistent with the recorded delivery state.

Connections, projects, decision rules, delivery settings and Markdown revisions are editable from the workspace. Connections are workspace-wide. Setup and reconnection ask for the provider and source. Project selection appears on tasks and decision rules. New connections offer provider sign-in first. GitHub can reuse the local GitHub CLI account or start a browser login. Slack accepts a user token. Google uses browser consent for Workspace services. Before saving, the user sees the verified account and connects their GitHub account, connects the Slack workspace, or confirms their Google account. Users can cancel, retry or enter credentials manually. Existing connections can be edited or reauthenticated. GitHub’s account row expands to show repository sync status. Browse work pages through open issues, pull requests and review requests. Review for work submits a monitored item to discovery. Passwords and authorization credentials stay out of browser storage. A missed-work report is accessible from activity. Activity and source text render as text. Dialogs are keyboard accessible and polling preserves open forms and the proposal the user is reviewing.

The sidebar links to [Settings](#settings), which lets the user select Claude Code or Codex CLI independently of delivery mode. Both choices are available even if their executable is missing. Settings shows each CLI's status, explains how to sign in using the CLI, and explains that the CLI may send supplied task context to its configured AI service. The user can recheck installation after installing a CLI. A pending style suggestion can be approved or declined. An investigation report links to each recovered task available in the queue.

**Context** shows when Hermes last used its context tools, every schedule with its timing, origin, reason and next run (with **Cancel**), and every context entry with its kind, project and review state (with **Retire** or **Restore**). Stale entries are labeled as withheld from agents. **Decision rules** lists handoff candidates above the rules. [Context and schedules](context-and-schedules.md)

## Overview dashboard

**Overview** is a dashboard: numbers first, a report on recent activity, and a chat with Hermes beside them. It replaces the Home layout's Orchestrator section and **Ask** dialog. Implemented in `ui/app.js` (`overview`, `renderOverview`).

- **Layout.** Two columns: the dashboard on the left, the Hermes chat on the right. The chat is pinned to the window height so its message box stays visible while the left column scrolls. Under 1180 pixels the chat moves below the dashboard. The left column's sections stack when it is narrower than 820 pixels.
- **Stats.** Need you (opens Inbox), In progress and Done in 7 days (open Tasks with that filter), Hermes started today against the daily safety limit (focuses the chat), and Events today (opens Activity). The setup card, when shown, sits above them.
- **Activity report.** A period switch (Today, 7 days, 30 days, remembered in the browser) drives:
  - a bar chart of activity events per hour (Today) or per day, one series in the app's green, with the count on hover and a text alternative listing every bar;
  - New tasks, Completed, Failed and Waiting for you. Completed and Failed count tasks whose last recorded event falls in the period. Waiting for you is the current Inbox count. Each number opens the matching list;
  - the five busiest sources (connection), projects and event kinds in the period.
  The report is computed in the browser from the activity log and tasks the app already sends. **Ask Hermes for a report** sends Hermes a plain prompt for the same period ("Report on my activity over the last 7 days: what came in, what you dispatched, what finished, what failed and what is waiting for me."). Its answer arrives in the chat.
- **Open tasks, suggestions, recent activity, connections, projects and style reviews** follow the report, as before. Open tasks lists up to eight tasks that need attention or are in progress, attention first.
- **Chat with Hermes.** The header shows Hermes' status (Idle, Answering…, Paused or Needs attention), when it last swept, **Sweep now** and **Pause**/**Resume**. A recorded error shows in a red strip. The thread shows the last 30 messages: yours on the right, Hermes' replies and digests rendered as Markdown with their task links and an action card per linked task ([message format and actions](hermes-orchestrator.md#message-format-and-actions)), and the app's own notices (such as "Hermes is not installed.") in amber. While Hermes is answering, a typing indicator shows and sending is disabled, because the service accepts one prompt at a time. Two quick prompts ("What's on my plate?", "What's stuck?") send a ready-made question. The message box sends with the button or **⌘↵**. Typed text survives the five-second refresh. The thread stays scrolled to the newest message unless you scrolled up to read.
- Hermes still has no tool to send anything. A request for work in the chat becomes a dispatched task, and its writes go through review in dry mode.

### Acceptance criteria

- Load the sample workspace and open Overview. The stats match the Inbox, Tasks and Activity counts, and each stat opens its view.
- Switch the report period. The chart, numbers and lists change to that period, and the choice survives a reload. Hovering a bar shows its count.
- Type in the chat, wait for a refresh, and the text is still there. Send with **⌘↵**. Your message appears, sending is disabled while Hermes answers, and the reply appears in the thread. With Hermes not installed, the reply is the app's notice and sending is available again.
- **Ask Hermes for a report** sends the prompt for the selected period.
- At 900 pixels wide every section is readable and the chat follows the dashboard.

## Settings

Settings is one page with four tabs. Each control sits on its tab and saves when it changes, so no dialog stands between the user and a setting. The tab is part of the address (`#settings?tab=agents`), so links from Setup, the toolbar and the sidebar footer open the right one. An unknown tab opens Delivery. Implemented in `ui/app.js` (`settingsPage`, `settingChanged`).

| Tab | Contents |
|---|---|
| **Delivery** (default) | Dry mode and Live mode as two radio cards, each saying what it lets leave without you, and a link to Decision rules. |
| **Agents** | *Task agent*: Claude Code and Codex CLI as a radio list with their state, version and **Sign in** when needed. The chosen one is marked *Prepares tasks*. A note says the CLI may send task context to its AI service. One **Check again** rechecks every agent. *Orchestrator*: the Hermes row with its state, a **Uses** subscription picker, **Sign in**, **Open dashboard** and **Retry install**. |
| **Instances** | This instance and every paired one, with Rename, Add checkout, Add instance, Join and Remove. With a paired instance, *This instance's share* adds **Tasks on this instance** (Run here first, Overflow only, Never run agents) and **Agent slots**. |
| **Workspace** | Folder access, the ignore list with its counts, and loading the sample workspace. |

- Choosing **Live mode** saves nothing yet. The radio stays on Dry mode and a dialog explains that agents will send without asking whenever every applicable rule allows the full action. **Turn on live mode** saves it. Closing the dialog keeps dry mode. Choosing **Dry mode** saves at once, because it only adds approvals.
- Every other change saves immediately and confirms in a notice, such as "Codex CLI now prepares tasks.". Changing the task agent or the Hermes subscription rechecks agent status.
- A failed save shows the server's error and puts the control back to the saved value.
- Agent slots save when the field loses focus or on Enter. It accepts a whole number from 0 to 64, or empty for the default. Typing in it survives the five-second refresh.
- Under 560 pixels the tabs tighten and each row's actions wrap under its text.

### Acceptance criteria

- Open Settings from the sidebar. Delivery is selected. Each tab opens its contents, and reloading keeps the tab.
- Choose Live mode, then close the dialog: dry mode is still saved and selected. Choose it again and confirm: the toolbar and sidebar footer say Live mode. Choose Dry mode: it saves without a dialog.
- On Agents, choose the other CLI. The *Prepares tasks* mark moves, the toolbar names it, and a reload keeps it. Change the Hermes subscription and reload: it is kept.
- With a paired instance, change Tasks on this instance and Agent slots, then reload: both are kept. An invalid slot count is refused with a message.
- Setup's **Change agent** opens Agents and its delivery **Change** opens Delivery.
- At 390 pixels wide every tab is readable and every control is reachable.

## Inbox view

The Inbox is the landing view. It has three columns: the sidebar, the task list and the open task. It follows the reference layout the user supplied on 2026-11-24. The [Overview dashboard](#overview-dashboard) remains available as **Overview**.

- **Sidebar.** Brand, then Overview, Inbox, Tasks, Activity, Projects and Connections. Inbox carries a badge with the number of tasks that need attention. Context, Decision rules, Skills & style, Setup and Settings follow. The footer names the agent provider and the delivery mode and links to Settings → Agents.
- **Header.** "Inbox", one line saying these tasks need the user to keep agents moving, and an **Auto-group** switch. The switch is remembered in the browser.
- **Summary cards.** Needs attention, In progress, Completed (24h) and Blocked. Each card filters the list or opens Tasks for that group. Completed counts done tasks whose last recorded event is under 24 hours old.
- **Filter chips.** All, Decision, Failed and Blocked, each with a count. Decision is a proposal awaiting approval or a question. Failed is a failed task. Blocked is a delivery whose outcome is uncertain or a question caused by an inaccessible checkout. **Project** narrows the list, cards and chips to one project, including its child projects, and **All projects** clears it. The choice is remembered in the browser. A project that no longer exists falls back to All projects. Opening a task from elsewhere that the filter hides clears it. **Sort by** offers Priority (failed, decision, blocked, then newest) and Newest.
- **Groups.** With Auto-group on, two or more failed tasks with the same first error line collapse under one header: "N tasks failed: <error>", with the projects or repositories affected and **Retry all**. Every other row that shares its repository with at least one other row, or its project when neither names a repository, collapses under "N tasks in <repository>" with a count by kind, such as "2 decisions, 1 failed". Repository names match regardless of case. A task belongs to one group only, and same-error failures take precedence. A group sits where its first row would be, and can be expanded and collapsed. With Auto-group off every row stands alone.
- **Rows.** Each row shows the title, the repository or project with its source icon, a status pill and the time since it was created. With a paired instance, the row also names the instance that owns the task, and "(here)" marks this one. Failed rows are red, decisions amber, blocked grey. Clicking a row opens it in the right column and marks it selected.
- **Shortcut answers stay on every row.** A question keeps its short answer buttons under the title, or its **Write an answer…**, **Choose checkout…** or **Allow folder access** control. Every row keeps its icon shortcuts (**A**, **V**, **R**, **F**, **O**, **C**) with the same keys while the row has focus. **J** and **K** move through rows, and **1–9** pick the selected question's numbered answer.
- **Open task.** Source and repository chips with an issue or pull request number when the title or link has one, then the title, status pill and age. A failed task shows its error in a red callout, which can be collapsed. A question shows the question and every answer with what it means. A review shows the full proposal: operation, sending account, destination, content and version. The action row holds only actions the task allows: Approve this version, Answer, Retry, Record outcome, Allow folder access, Instruct, Close, and a **More** menu with the full task dialog, Run on another instance and the ignore controls. There is no Pause or Redirect, because the service has no such operations.
- **Tabs.** Activity shows the task's events as a vertical timeline with icons. Details shows the facts, results and receipts. Context shows why it surfaced, the task Markdown and the supporting activity. Files appears when the task has a worktree or checkout.
- **Instruct box.** At the foot of the open task, "Instruct the agent…" sends feedback, or the answer when the task is waiting for one, against the version on screen. **⌘↵** sends. Typed text survives the five-second refresh and switching between tasks. The box is disabled with a reason when the task cannot take instructions, such as a closed task or an uncertain delivery.
- **Narrow windows.** Under 1100 pixels the open task replaces the list, with a **Back to inbox** button. Under 720 pixels the sidebar becomes the existing menu.

## Acceptance criteria

- A question in Home or Tasks shows one short prompt and up to three short answer buttons. Opening the task shows the context and what each answer means. A user can select an answer from either view or enter their own. Questions requesting a new fact may have no suggested answers. Clicking a choice records an answer only for the version shown. A stale choice fails without answering a newer question. Existing long questions remain answerable while the app prepares a compact presentation.

- Home, Tasks and supporting activity use recognizable icons for known sources such as GitHub, Slack and email. Icons have accessible names and hover labels. Task rows keep project, repository, workspace and account names visible and searchable. Unknown sources display their text. Connection controls name the provider for assistive technology even when its icon supplies the visual label.

- Task context renders Markdown headings, lists, emphasis, links, tables and fenced code offline. Raw HTML is inert, images make no network requests, and outbound approval previews retain their exact content.
- In Settings the user can edit the ignore list of named projects, GitHub repositories (owner/repo), and local checkout paths. Existing scopes remain visible for editing. A paused task shows its status.
- Home and Projects show **Ignore project** beside each named project. An explicit exclusion can be removed there. A child covered by a parent identifies the parent. In both task queues and suggestions, clicking a project or repository name opens its own details with the applicable ignore or unignore control. The task title opens the task independently. The names are individually keyboard accessible on narrow and wide screens. The queue’s **I** shortcut opens scope details. GitHub repository details include a link to GitHub, and local repositories show their checkout path. Task actions and the GitHub repository list also offer applicable exclusion controls. Before applying a change, show the exact project or repository and the effect on existing and future work. Changing one exclusion preserves all other entries.
- **Close task** in task details retires an open task locally and preserves its evidence. Closed tasks are available in the Closed filter and leave the Home queue. Legacy dismissed tasks remain accessible. An uncertain delivery must be reconciled before closure.

- On Home and Tasks, two tasks with the same title can be distinguished by their labeled project, repository when known, and source directly in the row. These labels wrap in a narrow window and appear in task details. A GitHub event identifies its owner/repository, a Slack event its channel when recorded, and an email event its originating mailbox account. Source information comes from the triggering activity even if a later action uses another account. A local task shows its project and Local. Only show a repository associated with the task itself. Queue search matches the displayed context.

- **Instance on every row.** With at least one paired instance, every task row in Inbox and Tasks and the open task name the instance that owns it, such as "On vps-8b778b72" or "On dodesbook1 (here)". The label is plain text, not a scope link. Tasks lists the tasks of every paired instance, and an instance filter (All instances, then each instance) narrows it to one. Search matches the instance name. Without a paired instance, no label or filter appears. Verify: pair two engines, create a task on each, and check that both dashboards list both tasks with the owner's name, that the filter shows only one instance's tasks, and that **Run on…** still offers this instance only for a task another instance owns.

- Task and activity filters for a named group include its child projects. The Global filter shows general work and All projects shows the complete workspace. The project editor lists its directly linked repositories and lets the user choose a parent for a named project. **Add repository** adds another row. For each row, **Choose folder…** opens the macOS directory picker. The chosen repository path appears in the form and is validated when the user saves. Users can replace or clear an existing selection. Cancelling preserves the form, including its current folder. The local browser interface also opens a native picker on the Mac running the service.
- Connect Google opens browser consent. After one Google account is connected, Add Google account opens a fresh account chooser. Reconnecting a particular row verifies its original identity. Manual registration remains available.

- Load the sample workspace and open Inbox. The cards and chips count the fixture tasks by the groups above. A question row shows its answer buttons and row shortcuts. Pressing a number key on the selected question answers it for the displayed version. Two failed tasks with the same error collapse into one group while Auto-group is on and separate when it is off. A decision and a blocked task on the same repository collapse into one "2 tasks in <repository>" group, a task on another repository stays alone, and turning Auto-group off separates them. Choosing a project in **Project** leaves only that project's rows and counts, and the choice survives a reload. Typing in the instruct box survives a refresh. Approve is the only path to send and still confirms the displayed version.
- Check Home with an empty workspace and with tasks, recent events and connected accounts. Empty sections show their empty states. In a populated workspace the counts match the queue, task and activity links open the corresponding views, and the Connections section offers exactly one action in either state.
- Selecting a row opens its project, status, source and recorded work. Filters and search update the displayed queue. Reported failures remain visible.
- Opening a task selects **Actions** and puts the available controls above the question, proposed change or result. **Why it surfaced & context** shows the reason, task Markdown, source and supporting evidence. **Task activity** shows its history, feedback and delivery receipts. The tabs support keyboard navigation. Switching tabs preserves the reviewed version and any stale-proposal warning.
- Home and Tasks offer shortcuts beside each task. Focus the row and press **A** to answer, **R** to retry preparation, **F** to give feedback, **C** to open the close confirmation, **V** to review a proposal or **O** to record a delivery outcome. Only applicable actions appear. The icon buttons show their keys on hover and work with touch. Review opens the exact version for a separate confirmation. Row shortcuts apply only while focus is on that task.
- A task waiting for an answer offers **Retry preparation** so the user can recheck its current project settings without entering the checkout path as an answer.
- **Settings → Workspace → Folder access** is available even when the queue is empty. A question caused by an inaccessible checkout opens the same controls from **Allow folder access** on the task. The user can choose the registered folder again in a native picker, open macOS Files & Folders settings after a denial, or check access after changing a permission. Show the selected checkout path and verify Git can read it from the service before reporting success. A successful check wakes the existing scheduler for eligible tasks. Cancellation, choosing another folder and a failed check preserve project registrations and pending decisions.
- For a review, compare the displayed version, account, target and exact content with the submitted approval version. A stale or failed approval displays the server error. Delivery with an uncertain outcome offers no resend.
- Open a form while another task changes. Typed text and keyboard focus survive the refresh. A form submission reports failure inline and preserves the user's entry.
- A connection can be configured through the provider schema. A project rule can be saved, a skill reviewed, and a missed-work report submitted. A fresh state request reflects each successful action.
- With fixture accounts, connect GitHub without selecting a repository, connect Slack without a channel picker, and confirm a Google account with its granted services. Verify browser links, device codes, one-time app registration, cancellation, retry and reauthentication. Manual setup remains reachable for all three providers.
- A narrow window keeps all main views and actions accessible. A keyboard user can open and dismiss a form, navigate views and return to the invoking control.
- With one CLI installed, check that Settings → Agents distinguishes the installed and missing providers. Choose either provider and reload. The selected provider persists and the delivery mode retains its saved value. Recheck after installation and verify that the status updates. A failed availability check offers a retry.
- Decline pending style guidance and observe its updated state. Open a completed report and follow a recovered task link to the matching task detail.
