# User stories

| ID | As the dashboard user, I want to… | Example outcome |
| --- | --- | --- |
| US-01 | Connect email, Slack, and GitHub to my workspace, choose what to follow across projects, and reconnect when access expires. | I connect my personal and work Google accounts through the same browser chooser. From Home I can manage connections and open a separate activity log for each. Connecting Slack enrolls my accessible channels automatically. [Account connections](specs/connectors.md) |
| US-02 | See tasks from incoming requests and understand what triggered them. | I can distinguish two review requests with the same title by their project and GitHub repository in the queue, then open either to see the pull request and why it surfaced. [Dashboard](specs/dashboard.md) |
| US-03 | Discover useful follow-ups even when no new message arrives. | The dashboard suggests revisiting an unanswered email and links the thread. |
| US-04 | Have the agent choose how to handle a task and get started on its own. | A reply is ready when I open the dashboard. I can correct it, add context, or dismiss it. |
| US-05 | Let the agent prepare work in dry mode and decide exactly what leaves my machine as a post or update. | I can review and confirm one Slack reply while an email draft stays pending. |
| US-06 | Eventually hand off familiar work completely. | With authority to handle routine status requests, the agent answers one, checks delivery, and records the result while I am away. |
| US-07 | Have a dedicated agent work on each task. | A delegated fix receives its parent's instructions and a private clone where it can run the project’s tests. The parent resumes when the fix supplies new evidence. [Task execution](specs/task-execution.md) |
| US-08 | Rely on promises I make or delegate being picked up later. | A sent reply promising Friday's figures creates a linked follow-up. |
| US-09 | See whether a task achieved its actual outcome. | A bug stays open on the dashboard until its issue, mergeable linked PR, and reporter notification are verified. |
| US-10 | Define how each project handles each type of decision. | One project allows routine replies while requiring review for promises. |
| US-11 | Teach my writing style through feedback and past posts. | The agent asks what an ambiguous edit means and future agents apply my approved preference. |
| US-12 | Decide when I trust autonomous delivery. | I can inspect missed tasks, work quality, and style fidelity before changing a project's rules. |
| US-13 | Leave work with the person already tackling it. | The dashboard shows why the agent skipped a claimed bug. |
| US-14 | Resolve blockers in dry mode while independent work continues. | I can pick a revised date directly in the queue, open the task to compare what each choice means, or restore folder access after missing a macOS prompt. [Dashboard](specs/dashboard.md) |
| US-15 | Review everything agents do and report omissions in the app. | Reporting a missed Slack request starts an agent that recovers outstanding related requests. |
| US-16 | Have agents improve through skills and other Markdown files. | A revised discovery skill catches a similar request on the next run using the same app version. |
| US-17 | Delegate general computer work in Global and group related repositories under a named project. | A GitHub issue finds its local project from the checkout’s origin. One release can include both client and service repositories. An unrelated email stays in Global. [Task execution](specs/task-execution.md) |
| US-18 | See suggested work grounded in my connected apps and activity on my Mac. | A follow-up from a Claude or ChatGPT conversation appears with its supporting exchange. A changed budget sheet and a Slack request can also support a suggestion. [Activity suggestions](specs/activity-suggestions.md) |
| US-19 | Use MeMyselfAI to improve itself. | I run the app's workflow checks or report something I observed. I can follow a finding from its test evidence through its GitHub issue, fix and pull request review in Tasks. [Self-improvement](specs/self-improvement.md) |
| US-20 | Clear what agents need from me like an email inbox, from the keyboard. | I open the app, press J and K through five rows, press 1 or E on each, and every agent continues. Working agents stay out of my way. I pick one project to see only its rows. [Inbox and focus card](specs/inbox-experience.md), [Inbox view](specs/dashboard.md#inbox-view) |
| US-21 | See all work at a glance by stage. | Press B and the board shows what was found, is queued, is working, needs me, is waiting, or is done, and where each agent runs. [Board](specs/inbox-experience.md#board) |
| US-22 | Approve a send quickly but safely. | I press E on a reply whose full text, account and destination are on screen, and it is sent at once. [Sending](specs/inbox-experience.md#sending) |
| US-23 | Have the agent find whole projects, not only single tasks. | A project for a trip discussed across mail, chat and my calendar appears with its tasks, without my asking. I can rename or merge it later. [Proactive discovery](specs/proactive-discovery.md) |
| US-24 | Connect more of the apps where my obligations live, including socials and messaging. | After connecting Bluesky and Telegram, mentions and DMs that need an answer get their own task agents, and replies reach me for approval. [Connector catalog](specs/proactive-discovery.md#connector-catalog) |
| US-25 | Run the agent on a VPS I own. | I install it on my server and open its dashboard through my desktop app or an SSH tunnel. [Instances](specs/instances-and-sync.md) |
| US-26 | Run on my laptop and VPS at the same time, as one workspace. | A task I create on the laptop shows on the VPS within seconds. When my laptop is full, new tasks run on the VPS. [Dividing work](specs/instances-and-sync.md#dividing-work) |
| US-27 | Keep discovery and work going while my laptop sleeps. | Overnight, the VPS reads my mail, prepares replies and leaves them in my inbox for the morning. |
| US-28 | Approve from any instance without risking a double send or double work, even when my VPS is down. | I approve on the laptop. The task's one owner instance sends it, at most once. With the VPS offline, the laptop keeps working and sending for its own tasks. [Ownership protocol](specs/instances-and-sync.md#ownership-protocol) |
| US-29 | Connect an account once and have every instance use it. | I connect Gmail on the laptop. The VPS polls it overnight without me signing in again there. Logins travel only between my paired instances. [What syncs](specs/instances-and-sync.md#what-syncs) |
| US-30 | Talk to the agent that runs discovery, and get updates from it. | I ask the orchestrator what is on my plate this week, and each morning it posts what it found, what finished and what needs me. [Hermes orchestrator](specs/hermes-orchestrator.md) |
| US-31 | Set up agents and accounts once, and have every kind of work flow the same way. | I sign into Claude once and connect Google once. The orchestrator reads my mail, hands an email that needs a reply to a new agent, and that agent writes and sends it through the app. A Slack mention or a meeting invite goes the same way. [Agents and the app MCP server](specs/agents-and-app-mcp.md) |
| US-32 | Be walked through setup, with the app doing whatever it can on its own. | On first launch the app opens on Setup. It already found Claude Code signed in, and connects my GitHub CLI account in one click. Only the steps that need me are marked. [Guided setup](specs/guided-setup.md) |
| US-33 | Set up my VPS from the desktop app using a host from my SSH config. | I pick OVH-VPS and choose Set up server. The app installs the service, installs Claude Code there and pairs the server with my Mac. It asks only for a sudo password, and for one sign-in in Terminal. [VPS setup over SSH](specs/guided-setup.md#vps-setup-over-ssh) |
| US-34 | Manage what the agent works on. | I can read a formatted issue description, exclude projects or repositories from agent work, and close a task when I have handled it myself. [Dashboard](specs/dashboard.md) · [Task workflow](specs/task-workflow.md) |
| US-35 | Have agents share what earlier work taught them, without seeing what isn't theirs. | A reply agent in a project knows the client's preferred contact and an open promise. It never sees another project's context. Stale context is held back until Hermes reviews it. [Context and schedules](specs/context-and-schedules.md) |
| US-36 | Get recurring work done on a schedule that follows what I ask for and what I've committed to. | I write "every Friday, summarize open PRs" in a task. Hermes creates the schedule, and each Friday a task appears. Cancelling it stops it for good. [Context and schedules](specs/context-and-schedules.md) |
| US-37 | Know which work is ready to hand off. | Decision rules shows that status replies in one project had 5 uncorrected deliveries. I allow autonomous handling in one click. [Context and schedules](specs/context-and-schedules.md) |
| US-38 | Install the app once and have it keep itself up to date. | I put MeMyselfAI in Applications. When a new version is published on GitHub, it downloads it, checks it, replaces itself and reopens on its own. [App updates](specs/app-updates.md) |
| US-39 | Have every open issue I wrote or own worked on, including ones older than my connection. | An issue I filed last month in a repository I connect today becomes a task. When its agent finishes, I approve a fix branch and PR in the inbox; it never closes silently with the edits left on disk. [Connectors](specs/connectors.md), [Task execution](specs/task-execution.md) |
| US-40 | Hear when work needs me, without keeping the dashboard open. | With the window closed, a notification says a reply needs my approval. I click it and that task opens. A task Hermes dispatched sends a short note when it finishes. Refreshes and restarts never repeat one, and I can turn them off in Settings. [Notifications](specs/dashboard.md#notifications) |

No task waits on me to run a build or test, extending US-07 and US-26. A fix prepared on the VPS moves to my Mac to build the app there. With the Mac asleep, the pull request says the build is still to verify. [Checks this machine cannot run](specs/task-execution.md#checks-this-machine-cannot-run)

Workspace-wide Slack and Google account connections extend US-01 and US-03. [Workspace accounts](specs/account-wide-connections.md)

US-01 through US-05 are covered by the [task workflow](specs/task-workflow.md), US-07 through US-09 by [task agents and completion](specs/task-execution.md), and US-06 and US-10 through US-12 by [decision rules, writing style, and trust](specs/delegation-and-style.md).

US-35 through US-37 are specified in [shared context and schedules](specs/context-and-schedules.md).

US-13 extends the [task workflow](specs/task-workflow.md). US-14 extends [decision handling](specs/delegation-and-style.md). US-15 and US-16 are specified in [reviewing activity and learning from missed work](specs/activity-and-improvement.md).

US-20 through US-22 are specified in the draft [inbox, focus card and board](specs/inbox-experience.md). US-23 and US-24 are specified in the draft [proactive discovery and connector catalog](specs/proactive-discovery.md). US-25 through US-29 are specified in the draft [instances, sync and sharing work](specs/instances-and-sync.md). US-25, US-28 and US-29 work today, except for logins held by other tools such as Google browser-profile sign-ins. US-26 and US-27 work too: queued tasks split by free agent slots, and the laptop hands its work to the VPS before sleeping or quitting. Coding tasks move with their worktree to an instance that has a checkout of the same repository. If an instance is lost, another takes over its work automatically after 15 minutes of silence. Pairing, moving connections and takeover never ask the user. Only repository writes and sends do. US-30 is specified in the draft [Hermes orchestrator](specs/hermes-orchestrator.md). US-31 is specified in the draft [agents, capabilities and the app MCP server](specs/agents-and-app-mcp.md).

The [desktop dashboard spec](specs/dashboard.md) maps these workflows to their user-facing controls.

US-32 and US-33 are specified in [guided setup and VPS setup over SSH](specs/guided-setup.md).
